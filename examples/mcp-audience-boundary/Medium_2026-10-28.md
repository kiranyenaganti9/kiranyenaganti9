# The token is valid. The destination is wrong.

A small MCP authorization example that checks the resource, the acting agent and whether dispatch actually happens.

Kiran Yenaganti · DataGovernAI · Technical design note

A support agent reads a customer record, then asks another agent to create a ticket. Both tools use MCP. The first call succeeds, so an adapter forwards the same access token to the second server.

That is not enough to authorize the second call. This note and its original educational code were prepared with AI assistance. The example implements existing security requirements; it does not introduce a new OAuth rule or report a production incident.

## Start with the destination

An authentic, unexpired token can still be wrong for the server receiving it. Permission to read a CRM does not automatically grant permission to create tickets somewhere else.

The MCP authorization specification requires protected MCP servers to validate that tokens were issued for their intended audience. Its security guidance explicitly prohibits token passthrough. These requirements apply within the specification’s HTTP authorization model; stdio has a different credential arrangement. [1][2]

Consider two fictional resources:

```text
CRM:      https://mcp.example.org/crm
Tickets:  https://mcp.example.org/tickets
```

A token intended for the CRM reaches the ticketing server. The ticketing server must reject it if it is not valid for that resource. It needs an appropriately authorized credential, not an adapter’s assumption that the previous request worked.

Scope and audience answer different questions. A scope describes permitted access. The audience identifies the intended resource. Two services recognizing the same scope name does not make their tokens interchangeable. RFC 8707 explains resource indicators and the wider trust assumptions involved in tokens with multiple audiences. [3]

This example deliberately accepts one exact audience identifier. Real deployments may use opaque tokens, introspection, configured identifier mappings or multiple audiences. A teaching function is not a substitute for that protocol implementation.

## The contribution in this example

The code brings a few checks into one small, executable decision path. It binds the proposed caller to an authenticated identity context, restricts which agents a subject may use to initiate work, and checks delegation against the particular resource and operation.

The point is to make those assumptions visible and testable. A token audience check alone cannot tell whether the acting agent is the caller that the integration authenticated. A delegation chain that ends with the right name is also insufficient if the application has never authorized its starting agent.

The sample uses these records:

- `TrustedClaims`: previously validated token information, including subject, issuer, audience, tenant, scopes and expiration.
- `TrustedIdentity`: the authenticated subject and acting agent supplied by trusted integration code.
- `ToolCall`: the proposed resource, operation and delegation chain.
- `Policy`: permitted initiating agents, accepted issuers, required scopes and resource-specific delegation capabilities.

The first two records must come from a trustworthy integration. Giving a Python class a reassuring name does not authenticate its contents. An agent must not be able to populate that context from its own tool arguments.

## Why the caller check matters

The initial version checked whether the last name in the delegation chain matched the proposed actor. Review exposed a gap: an unknown actor could provide a one-element chain containing its own name and pass that check. The token’s subject was also unused.

The revised example rejects a proposed actor that differs from the authenticated actor. It checks the token subject against the authenticated subject, then requires the chain’s starting agent to be explicitly authorized for that subject. Repeated names in the chain are rejected. Each delegation link must permit the requested operation on the intended resource.

These additions close those particular gaps in the local decision model. They do not prove that a real framework supplies trustworthy identity context or prevents another path from bypassing the function.

## A denial should change what executes

A function returning `DENY` does not establish that a tool call stopped. The caller might ignore the result and invoke the tool anyway.

The package therefore includes a small dispatch wrapper. It calls an injected transport only after an allow decision. Two tests observe a separate in-memory destination ledger: the allowed call reaches it once; a wrong-audience call leaves it empty.

All 18 tests pass locally. They cover valid direct and delegated calls, identity mismatches, an unauthorized starting agent, a delegation cycle, resource-specific delegation, issuer and audience mismatches, expiration, tenant, scope and unknown operations. They also cover the two dispatch observations.

That is evidence about this local wrapper. There are no network requests, real tokens or production effects. If an application can invoke the transport directly, it can bypass the wrapper. Process isolation, credential custody, token revocation and persistent audit records remain outside this example.

## What to test next

A useful next step is a controlled integration with two actual protected resource endpoints. Exercise the authorization flow, reject the wrong audience at the resource server, and observe the destination independently. Include successful requests so that a disconnected system cannot pass every negative test merely by doing nothing.

Also test a changed destination, a fabricated caller context and a tool path that attempts to avoid the checkpoint. Record the observed effect separately from the policy decision. A denied decision paired with an executed action is a failed boundary.

For engineers connecting agents to existing systems, that distinction is practical: which resource was authorized, which agent actually acted, and what happened after the decision?
